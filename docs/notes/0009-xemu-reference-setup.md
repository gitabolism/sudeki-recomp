# 0009 — xemu reference setup: install, SPIRITBOOT stall, VRAM question

**Observed (2026-11-21, sessions 4d-4e).** User approved installing xemu for
the reference baseline (rule 6 prerequisite). Install + first boot chain:

- xemu v0.8.139 AppImage (official GH release), digest
  `220282aacf09b30b35c55ba900a774fb6940c70deca1408bc70a4c9cc67c322f`,
  installed at `~/Applications/xemu/`. No pacman package exists on CachyOS.
- xemu requires flash + bootrom files (no HLE BIOS as of 0.8.139). We use
  the clean-room **SpiritBoot v1.1.0** (`optimized-xemu/SpiritBoot-checked.bin`,
  524288 B, sha256 per upstream SHA256SUMS OK) — no Microsoft bytes fetched.
  HDD: official `xemu-dashboard` `xbox_hdd.qcow2`
  (`00d7df7a…f6dd`). EEPROM auto-generated by xemu.
- ISO path with commas breaks QEMU option parsing → symlink
  `~/Downloads/xbox/sudeki-world.iso`.

**Wall: black viewport.** VM "running", UI renders, but the guest never
produces video. Diagnosis via QMP (`dump-guest-memory`) + HMP
(`info registers`):

1. At `-m 64` (xemu default): CPU sits with ESP=0, paging off, EIP in the
   flash mirror — early BIOS stall. Framebuffer aperture read as NOPs/code.
2. At `-m 128` (SpiritBoot's own README: images "passed direct xemu
   qualification at 128 MiB"; note xemu's `sys.mem_limit` config value must
   be the **string** `'128'`): EIP now advances (different values per 2 s
   sample), BUT the RAM dump at t=22 s shows **all 64 MiB of PC RAM zero**
   and **all 64 MiB of NV2A VRAM zero** — BIOS never initialized hardware
   or loaded the kernel. Only flash mirrors populated.
3. Conclusion: **SpiritBoot-checked does not complete boot on vanilla xemu
   0.8.139** (it is qualified against the Mainkill1/xemu fork).
4. Mainkill1 fork `v0.8.136-0-g458730bf5373` AppImage fetched, checksum OK
   (same dir). It ignores the new `sys.mem_limit` config key (needs `-m 128`
   QEMU passthrough) and never opens the `-qmp` telnet port — QMP-driven
   probing unavailable; RAM-evidence route pending on that build.

**VRAM side-question (user hypothesis: strata inference engine starves
xemu).** Measured: strata engine flags include `--vram-reserve-mib 700`
(it intentionally leaves ~700 MiB free); xemu's footprint measured ≈80 MiB;
free VRAM 697→558 MiB during a run; xemu's ImGui UI renders fine. GPU
starvation cannot explain all-zero *system* RAM at 22 s (a CPU/firmware
state). The falsification test (run xemu with the engine stopped) is
packaged in `scripts/xemu_standalone.sh` for the user — prediction: still
black. If the user sees boot animation, the contention theory wins and
interactive tests must use an idle-unload strata profile.

**STOP screen decoded (user screenshot + disasm cross-check).** With
`SpiritBoot-release.bin` + `-m 128` (the only combination that boots the
kernel), xemu shows the Xbox bugcheck screen:

`*** STOP: 0x0000007E (0xC0000005, 0x000226D8, 0x84FB8B1C, 0x84FB8820)`

- `0x000226D8` (faulting EIP) is **inside `sub_000223F0`, the boot-archive
  bitstream decoder** (funcs run 0x223F0→0x22720), at its output write loop:
  `0x226c0 mov eax,[ebp+0x18]; cmp eax,[ebp+0x1c]; jne 0x226d5;` flush path
  `call 0x22270` (**the same cache-writer/flusher our recomp traced**, the
  61,440 B chunk writer); `0x226d8 mov [eax], bl` faults with the *dest
  cursor* `0x84FB8B1C` past the mapped window.
- This is **the same runaway-destination-cursor failure we characterized
  in note 0007** (ours faulted at `0x84000000` = end of the 64 MB window;
  xemu at 128 MB lets it reach `0x84FB8B1C` before faulting). The decoder
  relies on the flush resetting the cursor; when the flush/stream end is
  mis-signalled, the byte loop walks off.
- Implication: **the reference environment reproduces our wall**. The
  xemu+SpiritBoot blue screen is NOT a clean title-screen baseline yet —
  its Z:/memory geometry also breaks this title. Strengthens H9/H10: the
  decoder never sees end-of-input in *either* environment, so the bug is
  in what the platform presents (stream EOF/short-read semantics, drive
  geometry), not in our lift.
- `-m 64` + release: RAM all zero at 22 s (kernel never loads) — worse
  than checked+64. Release+128 is the only live combo so far.
- xemu probe scripts now: `scripts/xemu_ref.sh`, `scripts/xemu_kill.sh`,
  `scripts/xemu_boot_probe.sh` (QMP retry fixed), `scripts/xemu_standalone.sh`.

- Frame reconstruction DONE — my own pixel evidence, not a screenshot:
  the `PT_LOAD @0xF0000000` segment of `dump-guest-memory` contains the
  NV2A framebuffer at VRAM offset **0x3C00000**, pitch **720 px**, BGRA.
  `reference/xemu/xemu-stop-screen.png` (gitignored) reconstructs the

**Harness lessons (encoded in scripts):**

- `scripts/xemu_ref.sh` — VRAM preflight (≥600 MiB free or refuse), bounded
  run, monitor-driven capture attempts.
- `scripts/xemu_kill.sh` — pattern lives in the file; `pkill -f 'xemu…'`
  from an inline shell matches the caller's own command line (SIGTERM 143
  mystery) — never pattern-kill from a line that contains the pattern.
- `scripts/xemu_boot_probe.sh` — boots xemu, QMP `dump-guest-memory` ELF,
  offline non-zero-page + title-string analysis.
- HMP over telnet mangles long commands (readline completion); use QMP
  JSON. `screendump` is stripped from xemu's HMP **and** QMP. The built-in
  screenshot is `F12` → but uinput-synthesized keys only reach xemu when
  its window has Wayland focus (unfocused = KDE Spectacle ate the key and
  wrote to `~/Pictures/Screenshots`). `qdbus6 org.kde.KWin /Scripting
  org.kde.kwin.Scripting.loadScript <js>` activates the window
  (`/tmp/opencode/kwin_focus_xemu.js`, loadScript returned 0; F12 delivery
  not yet re-verified after activation).
